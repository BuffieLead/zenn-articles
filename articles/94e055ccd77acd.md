[asdf](https://asdf-vm.com/)は、Node.jsやPythonなどのツールをプラグイン経由で管理できるバージョンマネージャーです。その日常的な操作を補うために、[asdf-extras](https://github.com/eihu0F/asdf-extras)というCLIを作りました。インストールしたバージョンの有効化や、プラグインとツールの更新をまとめて扱えます。

asdf-extras自体もasdfプラグインとして登録・インストールできます。さらにシェルを初期化すると、`asdf update`や`asdf install -u`のように、普段の`asdf`コマンドから追加機能を呼べます。

この仕組みを作るうえで大きかった設計判断は、**shell functionを`asdf`の上に重ねること**と、**asdfプラグインとCLIを同じリポジトリに入れること**です。この記事では、作った動機とともに、この二つの設計を説明します。

## なぜ作ったか

`asdf`でツールをインストールした後にバージョンを有効化する、プラグインとインストール済みバージョンを更新する。こうした操作を日常的に行うので、ひとまとまりのコマンドにしたかったのが出発点です。

たとえば、`asdf-extras install nodejs 24.11.0`はインストール後に`asdf set --home`で有効化します。`asdf-extras update nodejs`は対象の現在のバージョンと更新先を比較し、変更があればインストール・有効化・以前のバージョンの削除まで扱います。

ただ、毎回別のコマンド名を思い出すより、普段の`asdf`から使えるほうが自然です。そこで一つ目の設計につながりました。

## 1. shell functionを`asdf`に重ねる

[asdfの0.16への移行ガイド](https://asdf-vm.com/guide/upgrading-to-v0-16.html)によると、0.15以前のasdf本体はBashスクリプト群で構成されていました。コマンドの入口も[`bin/asdf`](https://github.com/asdf-vm/asdf/blob/v0.15.0/bin/asdf)というシェルスクリプトです。一方、シェルに読み込む[`asdf.sh`](https://github.com/asdf-vm/asdf/blob/v0.15.0/asdf.sh)は同名の`asdf`関数も定義していました。この関数は、現在のシェルの環境変数を変える`asdf shell`を処理し、ほかのコマンドは`bin/asdf`へ渡すラッパーでした。

0.16では本体がGo製の実行ファイルになり、このシェル関数はなくなりました。`asdf update`も0.16で削除されています。

asdf-extrasは、**現在のasdf本体を変更せず、シェル側に`asdf`関数を置く**方法を選びました。0.15以前と同じく関数をラッパーとして使いますが、asdf-extrasでは追加コマンドの振り分けを担います。

~~~bash
eval "$(asdf-extras init bash)"

asdf update nodejs
asdf install -u nodejs 24.11.0
~~~

`init`が出力するコードを読み込むと、[`lib/init/bash.sh`](https://github.com/eihu0F/asdf-extras/blob/main/lib/init/bash.sh)の`asdf`関数が有効になります。`update`はasdf-extrasへ、`-u`や`-p`など拡張オプション付きの`install`もasdf-extrasへ渡します。通常のコマンドは`command asdf "$@"`で元のasdf実行ファイルへ渡します。

~~~mermaid
flowchart TD
    A["シェルで asdf を実行"] --> B{"asdf-extrasが扱う操作か"}
    B -->|はい| C["asdf-extrasのコマンド"]
    B -->|いいえ| D["asdf本体の実行ファイル"]
~~~

シェル初期化はBashのほか、Zsh、Fish、Elvish、Nushellにも用意しています。初期化しない場合は`asdf-extras update ...`のようにCLIを直接実行できます。この場合、`asdf`コマンドは読み替えられません。

## 2. pluginとCLIを同じリポジトリに入れる

もう一つは配布方法です。[asdfのプラグイン](https://asdf-vm.com/plugins/create.html)はGitリポジトリで、`bin/list-all`、`bin/download`、`bin/install`などのスクリプトを通してツールのバージョン管理を提供します。この仕組みを使えば、**asdf-extras自体もasdfの管理対象にできる**と考えました。

このリポジトリには、プラグイン用の`bin/`と、CLI用の`libexec/`・`lib/commands/`が同居しています。

* `asdf-extras/`：リポジトリのルート
  * `bin/`：asdfプラグインの入口
  * `libexec/`：CLIの入口となる`asdf-extras`を配置
    * `asdf-extras`：CLIの実行ファイル
  * `lib/`：CLIの実装
    * `commands/`：install、update、initなどの実装
    * `init/`：各シェルの関数

導入は二段階です。

~~~bash
asdf plugin add asdf-extras https://github.com/eihu0F/asdf-extras.git
asdf cmd asdf-extras install asdf-extras latest
asdf-extras --help
~~~

最初の`asdf plugin add`で、asdfがプラグインのGitリポジトリを取得します。この段階では、asdf-extrasのCLIを使うためのインストールはまだ必要です。二行目は、プラグイン側にあるコマンドからasdf-extras自身をインストールするためのブートストラップです。

実装上、[`bin/download`](https://github.com/eihu0F/asdf-extras/blob/main/bin/download)はプラグインのチェックアウトを参照し、[`lib/utils.bash`](https://github.com/eihu0F/asdf-extras/blob/main/lib/utils.bash)で指定バージョンのタグまたはrefを解決して`git archive`で内容を取り出します。続く`bin/install`がその内容をasdfのインストール先へ配置し、`asdf-extras`実行ファイルを作ります。つまり、**プラグインとして取得した同じリポジトリを、CLIのバージョン付き配布元にも使っています**。CLI用に別のリポジトリを用意していません。

このため、`asdf cmd asdf-extras`はプラグインのチェックアウト内の実装を使い、`asdf-extras`はasdfが選択したインストール済みバージョンを使います。導入前後で同じ名前のツールに二つの入口がある理由も、この構成から説明できます。

## 二つを組み合わせる

プラグインがCLIをインストールし、そのCLIの`init`がshell functionを生成します。shell functionは必要な操作だけをCLIへ渡し、通常の操作はasdf本体へ渡します。

~~~mermaid
flowchart LR
    A["asdfプラグインとして登録"] --> B["同じリポジトリからCLIをインストール"]
    B --> C["CLIのinitをシェルへ読み込む"]
    C --> D["普段のasdfコマンドに拡張機能を重ねる"]
~~~

これがasdf-extrasの中心的なアーキテクチャです。0.15以前のasdfが本体のシェルスクリプトに薄い関数を重ねていた構成を参考に、0.16以降の実行ファイルにも追加機能を重ねています。プラグインの仕組みはCLI自身の配布にも使っています。実際のコマンドと対応バージョンは[README](https://github.com/eihu0F/asdf-extras#readme)を参照してください。
